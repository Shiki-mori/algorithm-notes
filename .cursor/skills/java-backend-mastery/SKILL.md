# Java 后端笔试面试掌握度推荐

用户当前的需求为通过Java后端岗位的笔试与面试。根据该需求为用户对该题目的掌握程度做出推荐。用户可能泛指整道题目，也可能指定该题目中的某个特定解法。

本 skill 只评估掌握深度，不改代码、不补题解，除非用户另外要求。

## 适用范围

仅处理 `algorithm/src/main/java/com/phrolova/algorithm/leetcode/` 下的题目目录（`pXXXX_slug/`）。

- 目标不在该目录：一句话说明范围后停止，不要对排序笔记、公共类或其他模块做推荐。
- `leetcode/common/` 不是题目，不要当题评估。

## 工作流程

1. **锁定目标**
   - 整题：用户说题号、题名、当前文件/目录，且未点名解法。
   - 特定解法：用户点名方法名、题解小节、或「DP / 组合数 / 快选」等具体思路。
   - 目标不清：先列本题已有解法（Java 方法名 + 一句话），再评估用户所指的那一个；无法判断时只问一句。
2. **读材料**（按存在情况，缺了就跳过）
   - `Problem.md`：难度、标签、约束
   - `Solution.md`：各思路与复杂度
   - 同目录 Java 类：每个 public 解法方法算一种解法
   - 题解空白时以代码为准；代码与题解冲突时以代码为准，并在理由里点明
3. **按笔试/面试分别判断**，标准见 [criteria.md](criteria.md)
4. **按下方模板输出**，不要展开讲题。完整样例见 [examples.md](examples.md)

## 掌握等级

只使用这五档，整题与单解法同一套词：

| 等级 | 含义 |
| --- | --- |
| 必须手写 | 闭卷限时能独立写对，作为笔试/面试主解 |
| 必须讲清 | 要能口述思路、复杂度、边界和与主解的对比；不强制默写每个细节 |
| 建议掌握 | 中高频或加分项，时间够就刷到手写 |
| 了解即可 | 知道存在、适用场景、为何不作为主解 |
| 可以跳过 | 对过 Java 后端笔试/面试帮助很小 |

整题等级取「主推解法」应达到的最高必要档，不要因为旁支解法抬高整题。

## 输出模板

### 整题

```markdown
## 掌握建议：<题号>. <题名>

- 范围：整题
- 总体：<等级>
- 主推解法：<方法名或思路> — <等级>

### 笔试
<2–4 句：会不会考、限时该写哪一版、卡点>

### 面试
<2–4 句：怎么讲、常见追问、要不要对比其他解法>

### 各解法
| 解法 | 等级 | 一句话理由 |
| --- | --- | --- |
| <方法名或小节标题> | <等级> | <理由> |

### 投入
- 先做：<一条>
- 可后做 / 可放下：<一条>
```

### 特定解法

```markdown
## 掌握建议：<题号>. <题名> / <解法名>

- 范围：特定解法
- 该解法：<等级>
- 相对本题其他解法：<主推 / 备选 / 引入 / 不建议投入>
- 手写还是讲清：<必须手写 | 必须讲清 | 不必手写>

### 笔试
<2–3 句>

### 面试
<2–3 句>

### 理由
- <相对本题其他解法的优先级>
- <对 Java 后端岗的迁移价值：模板、API、还是纯数学>

### 投入
- <一条下一步；旁支解法则写「把时间留给主推解法」>
```

## 约束

- 用中文，短句。理由要落到「笔试限时 / 面试追问 / Java 后端高频模板」，不要空泛说「很重要」。
- 同一题多种解法必须给出相对优先级；指定解法时也要提一句它相对主推解法的位置。
- Java 后端优先：`HashMap` / `PriorityQueue` / 双指针 / BFS / 树 DFS / 基础 DP。手写堆、组合数细节、竞赛向优化默认降档，除非它就是本题面试常追问点。
- 不要把题解或代码大段复述进回复。
